# Falcon-512 Signing Internals

QuantaChain uses two separate Rust crates that both implement Falcon-512. They coexist because each solves a different deployment constraint.

---

## The Two Libraries

### pqcrypto-falcon

Rust FFI bindings over the official NIST reference C implementation of Falcon-512.

- Compiles the C reference code and calls it from Rust.
- Authoritative, standards-compliant Falcon-512 key generation and signing.
- Cannot be compiled to WebAssembly. The C compiler dependency (`cc`) causes WASM compilation to fail.

### falcon-rust

A pure Rust implementation of Falcon-512, with no C dependencies.

- Compiles cleanly to WebAssembly, Linux, macOS, and Windows.
- Required for the browser wallet (`quanta-wasm`) because browsers execute WASM, not native binaries.
- Produces signatures in a different byte layout than `pqcrypto-falcon`.

---

## The Signature Format Difference

This is the critical point. Both libraries implement the same Falcon-512 cryptographic algorithm. However, their output byte formats differ.

`pqcrypto-falcon` returns a `SignedMessage` whose bytes are:

```
[ signature_bytes ][ message_bytes ]
```

`falcon-rust` returns a `Signature` whose `.to_bytes()` output is:

```
[ raw_signature_bytes ]
```

The node's verification function (`verify_signature_strict`) expects the blob format produced by the WASM wallet using `falcon-rust`:

```
[ raw_signature_bytes ][ 32-byte SHA3-256 hash ]
```

Where the last 32 bytes are the domain-separated hash that was signed, appended manually. Any transaction signed with `pqcrypto-falcon` and submitted to the node will be rejected with `invalid_signature`, even if the key pair is valid.

---

## Where Each Library Is Used

| Component | Library | Reason |
|---|---|---|
| Node key generation | pqcrypto-falcon | Authoritative key generation |
| `sign_transaction_canonical()` | pqcrypto-falcon | Native tool signing path |
| `verify_signature_strict()` | falcon-rust | Accepts WASM wallet format |
| Browser wallet (quanta-wasm) | falcon-rust | WASM requires pure Rust |
| Faucet distributor | falcon-rust | Must produce node-accepted signatures |
| Benchmark stress test | falcon-rust | Must produce node-accepted signatures |

---

## Correct Signing Pattern for Node Submission

Any code that produces transactions for submission to the live node must sign with `falcon-rust`:

```rust
use falcon_rust::falcon512::{self as fr, SecretKey as FrSK};
use sha3::{Sha3_256, Digest};

const SIGNING_DOMAIN: &[u8] = b"QUANTA_TX_V1:";

fn sign_for_node(sk_bytes: &[u8], signing_data: &[u8]) -> Vec<u8> {
    let mut h = Sha3_256::new();
    h.update(SIGNING_DOMAIN);
    h.update(signing_data);
    let mut hash = [0u8; 32];
    hash.copy_from_slice(&h.finalize());

    let sk = FrSK::from_bytes(sk_bytes).expect("invalid SK");
    let sig = fr::sign(&hash, &sk);
    let sig_bytes = sig.to_bytes();

    let mut blob = Vec::with_capacity(sig_bytes.len() + 32);
    blob.extend_from_slice(&sig_bytes);
    blob.extend_from_slice(&hash);
    blob
}
```

Set `tx.signature = sign_for_node(&sk_bytes, &tx.get_signing_bytes())`.

Do not use `FalconKeypair::sign_transaction_canonical()` for transactions that will be submitted to the live node.

---

## Public Keys Are Compatible

Public keys generated by either library use the standard 897-byte Falcon-512 encoding and are interoperable. A key pair generated with `pqcrypto-falcon` can be verified against a `falcon-rust` signature without any conversion, as long as the signature blob is in the correct format.

---

## Recommended Path Forward

The cleanest long-term resolution is to unify all signing under `falcon-rust`, which is both WASM-compatible and produces the format the node verifies. `pqcrypto-falcon` can be retained only for key generation until `falcon-rust` key generation is fully validated, then removed to eliminate the dependency on C compilation.
